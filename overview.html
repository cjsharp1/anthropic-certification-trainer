What it is

Exam preparation for the Anthropic Partner certifications: Associate (CCAO-F), Developer (CCDV-F), Architect Foundations (CCAR-F) and Architect Professional (CCAR-P). It holds a question bank, concept-first study notes, Leitner flashcards, hands-on labs and a readiness model that tries to say whether a projected score can be trusted yet.

It is built to be passed to a colleague. The whole app ships as one HTML file: double-click it and it runs. Progress lives in that browser's localStorage, so sending someone a newer build never disturbs what they have already answered.

Measured

The shipped build is 1.9 MB in a single file. It makes no network requests of any kind — no fetch, no XMLHttpRequest, no dynamic import(). The only external reference in the entire app is a Google Fonts stylesheet, and every family declares a local fallback, so the app is fully functional with no connection.

The Architect Foundations track carries a second, separate bank. After a real sitting of that exam, 270 scenario questions were written to match what the exam actually asks: long plain-prose stems with numbers scattered through them, four options where two would work, and one best answer. Those questions never mix into the recall drills.

Tech stack

Runtime dependencies

There are none. No package.json, no lockfile, no node_modules. Nothing in src/ calls require() or imports a module. The browser loads plain scripts that assign globals, in the order index.html lists them.

Why this stack

The constraint that produced it is distribution. The app has to reach a colleague who will not install anything, and it has to keep working offline. That rules out a bundler, a server and a package tree, and it makes the single-file build the product rather than a convenience. Everything else follows: globals instead of modules because the browser loads bare scripts, hand-written suites instead of a runner because adding a runner would add the first dependency.

The one structural concession is tools/paths.js. Tools and tests name app files by bare filename, and that one file maps a name to a directory, so moving a file between src/ and src/data/ is a single edit rather than an edit in twenty-seven scripts.

How it was built

The project has no git history and no build plan. This sequence is reconstructed from the verification log, the generated-file headers and the structure of the test suites, each of which records what it was written to catch.

  1. Blueprints first.

    The four exam blueprints in data-exams.js — domains, weights, question counts, pass marks — came before any question. Domain weights must sum to 100.0 per exam, and validate.js still asserts it on every run.

  2. Recall bank, written in batches.

    764 questions across 20 data files. A question carrying a domain id that does not exist in its exam would be silently excluded from drills rather than error, so the validator checks domain ids against the blueprint.

  3. Held-out and hard tiers split off.

    267 questions reserved so a practice exam can draw material the drills never show, plus a 65-question hard tier. Every hard-tier answer is checked against a primary source before shipping, logged in docs/VERIFICATION.md.

  4. Notes, flashcards and labs.

    27 notes covering 100% of exam weight, 194 flashcards, 19 labs. Card progress is keyed on exam, domain and the first 40 characters of the front, so colliding fronts would overwrite each other's progress — the validator checks for that collision.

  5. Exam Simulation, after a real sitting.

    The real CCAR-F exam did not resemble the practice material. A separate 270-question bank was built to match it, with per-option explanations, a tiebreaker naming what separates the best answer from the runner-up, and the 37 score-report objectives.

  6. Import pipeline retired.

    The simulation bank was generated by an importer from JSON drops. Once the question sets were final, the importer and its input were deleted and the generated files became the source of truth. The integrity checks the importer ran on every import moved into section 12 of the simulation suite, so nothing was lost with it.

  7. Per-objective coverage levelled.

    Drilling by objective was uneven: the 37 objectives ranged from 2 to 24 questions each. 62 questions were written to bring every objective to at least 8. A test now asserts that floor so it cannot silently regress.

  8. Projection moved to the simulation pool.

    The projected score was computed from drill history. Because the simulation questions match the real exam's shape, the projection now comes from simulation attempts where a simulation bank exists, and falls back to drill history where it does not.

  9. Fact-based verification pass.

    118 of the 270 simulation questions turn on a documented fact rather than a judgement. They were grouped into 16 topic clusters and checked against the product documentation. Three questions had a wrong correct answer; five more were annotated where the product had been renamed under them.

Gotchas worth keeping

  • Score reports are personalA real candidate's per-objective percentages shipped in the bank as reference data. For a colleague with a different report, or none, those numbers describe someone else's weak spots. Removed.
  • Two sources of truth for sittingsThe timed-sitting gate reads both simulation attempts and the retired timed mock's sessions. A reset that cleared only the first left the gate still reporting sittings afterwards.
  • Scenario identity is an idSource data spells the same scenario two ways. Everything resolves to a stable id; the display string is never matched on.
  • Tests pin behaviour, not arraysThe simulation reset test asserts the gate's view afterwards, not just that the array emptied. That is the assertion that caught the missed source.

Conventions

  • No runtime dependenciesNothing in src/ may require a module or make a network call. The single-file build depends on it.
  • Everything guardedEvery localStorage read and write sits in a try/catch. The app renders correctly when storage throws or returns nothing.
  • Pools never mixsim.js touches neither S.history nor S.sessions; simulation results live in S.simAttempts. A test greps the source to enforce it.
  • Answers keyed, not positionalOptions shuffle per attempt, so an answer is stored by option key. Option text never refers to another option by letter.
  • Destructive actions are typedEvery reset is gated behind typing an exact phrase. A single confirm dialog is clicked through by muscle memory.
  • Progress is per-browserNo account, no sync, no telemetry. One storage key, local to the machine. Shipping a new build never touches it.
  • Type scale is enforcedui-audit.js rejects any font size off the 17-step scale and checks heading levels.
  • Sources recorded per questionHard-tier and simulation answers carry source links. Where a claim rests on reasoning rather than a document, it is labelled inference with its premises named.

Caveats

Verification is partial by design. Of the 270 simulation questions, 118 rest on a documented fact and have been checked against the product documentation. The other 152 turn on a judgement about architecture, where the answer is a defensible design call rather than something a source can confirm. Those have not been through a verification pass, and the status table in docs/VERIFICATION.md says so rather than implying the whole bank is verified.

Provenance is the weaker half. 230 of 270 simulation questions cite only the exam guide, which establishes what is in scope but rarely settles whether an answer is right. 124 of those citations point at third-party mirrors of the guide rather than at Anthropic's own partner site.

The material has a shelf life. Pearson VUE lists an exam update for 2026-12-07, with refreshed guides due 2026-11-17. Claude Code moves faster than the exam guide: the fact-check already found the Task tool renamed to Agent, and three documentation URLs consolidated. The CLI, hooks, subagent and MCP clusters are the ones to re-check first.
